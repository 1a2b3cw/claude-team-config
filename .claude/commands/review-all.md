# /review-all - 多维度联合审查

合并前 / 上线前的全面审查。6 个维度一次完成，有问题自动修。

## 和 /check 的区别

| 维度 | /check | /review-all |
|------|--------|-------------|
| **目的** | 写完一个功能后快速查错 | 合并前/上线前全面审查 |
| **范围** | 当前变更的文件 | 整个模块或分支 |
| **维度** | 3 个（逻辑 + 类型 + 边界） | 6 个（+ 安全 + 性能 + 无障碍） |
| **耗时** | < 1 分钟 | 3-5 分钟 |
| **后续** | 有问题自动修 | 有问题自动修 → 重审 |

## 审查范围

**不带参数**：审查当前分支相对于 main 的所有变更
```
/review-all
# 等价于审查 git diff main...HEAD 中的所有文件
```

**指定路径**：审查指定文件或目录
```
/review-all src/features/auth/
/review-all src/auth/login.ts
```

**指定描述**：审查与描述相关的代码
```
/review-all 最近的变更
/review-all 用户认证相关的代码
```

## 6 个审查维度

### 1. 正确性
- 逻辑正确、边界条件、空值/undefined 处理
- 错误处理完善、并发/异步正确
- 函数返回值符合预期类型
- 条件分支覆盖所有情况

### 2. 安全性
- **注入**：SQL 参数化、XSS 转义、命令注入
- **认证**：JWT 最佳实践、密码哈希
- **授权**：RBAC 权限检查、水平/垂直越权
- **密钥**：无硬编码、环境变量管理
- **输入验证**：Zod schema、allowlist > denylist
- **依赖**：npm audit 无 high/critical

### 3. 性能
- N+1 查询、不必要的重渲染、内存泄漏
- 大数据分页/流式处理、图片优化
- API 响应时间 P95 < 200ms

### 4. 可维护性
- 命名清晰、单一职责、无重复代码
- 复杂度可控、注释必要且准确
- 文件组织符合项目规范

### 5. 测试
- 核心逻辑有测试、测试有意义
- 边界条件测试、测试独立可重复
- 覆盖率：语句 > 80%，分支 > 70%，函数 > 90%

### 6. 无障碍
- 关键交互元素有 aria 标签
- 颜色对比度达标（WCAG AA）
- 键盘可操作、语义化 HTML

## 审查流程

```
1. 确定审查范围
   - 不带参数 → git diff main...HEAD
   - 带参数 → 指定路径或描述

2. 快速扫描
   - 了解变更范围和目的
   - 识别变更类型（新功能/修复/重构）

3. 逐文件审查（6 个维度）
   - 按文件逐项检查
   - 交叉验证：变更之间是否一致

4. 整体评估
   - 架构和设计层面
   - 是否引入新的技术债

5. 输出报告
   - 按严重程度分类（严重/中等/轻微）
   - 每个问题附带修复代码

6. 自动修复（有问题时）
   - 严重问题 → 必须修，自动修
   - 中等问题 → 自动修
   - 轻微问题 → 列出建议，你决定
   - 修完后重新审查，最多 2 轮
   - 2 轮后仍有问题 → 列出剩余问题等你决定
```

## 后续动作

### 审查通过
- 可以合并 / 可以上线
- 输出："✅ 审查通过，可以合并"

### 审查不通过（自动修复后通过）
- 自动修复了 N 个问题
- 重新审查通过
- 输出："✅ 已修复 N 个问题，审查通过，可以合并"

### 审查不通过（2 轮后仍有问题）
- 列出剩余问题
- 等你决定：继续修 / 先合并标记 TODO / 放弃
- 输出："🔴 2 轮修复后仍有 N 个问题，请决定处理方式"

## 审查原则

- **解释 WHY**，不只说 WHAT
- **提供修复代码**，不只指出问题
- **区分"必须改"和"建议改"**
- **安全问题零容忍**，标记为严重
- **一次审查一个范围**，不扩大范围
- **审查结果可追溯**，输出完整报告

## 使用示例

```
# 合并前审查（最常用）
/review-all

# 审查特定模块
/review-all src/features/auth/

# 审查特定文件
/review-all src/auth/login.ts

# 审查最近的变更
/review-all 最近的变更
```

## 边界

- `/review-all` 是**合并前**的全面审查，比 `/check` 更重
- 日常开发中用 `/check` 快检，合并前用 `/review-all`
- 如果你只描述了"帮我看看这个文件"，AI 会用 `/review` 单文件审查
- 审查范围不超过你指定的范围，不会"顺手"审查其他代码
